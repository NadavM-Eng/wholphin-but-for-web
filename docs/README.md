# Wholphin Web documentation

The front door to the project's documentation: what the project is, where it stands, and in what order to read the rest.

Last updated: 2026-11-24

## What this project is

Wholphin Web is an unofficial web rebuild of Wholphin, an Android TV client for the Jellyfin media server ([github.com/damontecres/Wholphin](https://github.com/damontecres/Wholphin), release v1.1.1, upstream commit `8dcf189`). The goal is the same look and the same features as the TV app, in a browser: desktop first, but also tablets and phones, driven by mouse, keyboard or touch, with a layout that fills the window instead of a fixed TV screen. The scope includes the TV app's Seerr integration (Seerr is the request manager people use to ask for titles that are not in the library yet) and video playback inside the browser, letting Jellyfin remux or transcode only when the browser cannot play a file directly. Like upstream it is licensed under version 2 of the GNU General Public License (GPL-2.0-only), with an additional permission for three Apache-2.0 components in the root file [LICENSE-EXCEPTION.md](../LICENSE-EXCEPTION.md), and it is not affiliated with the Wholphin author or with Jellyfin. Technically it is a React and TypeScript single-page app plus a small server, shipped as a Docker image, that serves the app and forwards Seerr requests.

The owner, who runs a Jellyfin server and shares it with other people, asked the lead (an AI orchestrator) to build it with many AI agents and to document everything for a review at the end. The lead had the Kotlin source turned into written behavior specs, had those specs audited claim by claim, wrote the working agreement every agent follows, and then ran the build in waves: builders, independent reviewers, fixers and an integration or gate step for each part. Later waves ran side by side on separate branches, which a dedicated agent then merged, independent checkers examined and a repair agent fixed. These documents were written from the repository and from the agents' own reports.

**Current state:** the project is published and in maintenance. Every planned feature is built. `main` is at commit `d036067` (2026-11-24, plus the documentation update that follows it) in the private repository, which keeps the full history; the public repository holds three releases, each one commit on top of the other: the first, published on 2026-11-18 as a clean copy, the second, published on 2026-11-24, up to and including phase 35, and the third, published the same day, which carries the tree of `main` after the documentation commit of phase 39 (see "Two repositories" under Terms). The app runs as a trial in a container built from `d036067`. The work of phases 36 to 38, made after the second release, is in the third: the new order of Settings, the subtitle fix, the mouse on the episode strip and the language list in a fitted solid box (all on the trial) and the code map (`CODE-MAP.md`, documentation and tooling). [STATUS.md](STATUS.md) has the details, the latest checks and what is still open. The rest of this paragraph tells how the build ended on 2026-11-18; the next one tells what came after. The final merge brought branch `wave3a` (playback, settings, Seerr, the production server, Live TV, music, photos and the screensaver) and `main` (sign-in, the shell, Home, browsing, detail pages, search, the end-to-end suite and the fix pass) together on branch `integration` in two stages, each examined by independent checkers and repaired, followed by focus fixes after the audit (`main` was moved to `integration`, commit `c14b168`, on 2026-11-18). A separate pass then compared every screen with 244 pictures of the TV app (the TV-comparison pass, branch `parity`). On branch `final` that pass was merged into the app, with the rule that the comparison pass decides how things look and the repaired app decides how they behave; thirteen independent checkers examined the result from different angles, area fixers repaired the 47 findings, an integrator ran every gate, and an independent audit found it ready to land. A last job made the dynamic backdrop colors match the TV (branch `colors`, merged into `final`). On 2026-11-18 the lead moved `main` forward to `final` without a merge commit. A polish round then closed most of the points that were still open (six fixers side by side, an integrator and an independent verifier, on branch `polish`); the lead merged it into `main` (merge commit `f1fb308`), corrected one end-to-end test (`c358a52`) and pushed. A closing round the same day brought the documents up to date, retook the README's screenshots and fixed how numbers and units are drawn in right-to-left languages (`692715f`). The owner then gave the go for a trial behind their own reverse proxy, opened the app on a phone and reported that everything works; the one touch problem the owner named, a scroll that starts on a slider, was fixed at once (`7ad52ba`). On `main` at `7ad52ba` the 776 unit tests and all 250 end-to-end tests passed, and the CI run on GitHub succeeded. The trial first ran a container built from `7ad52ba`. The branches `integration`, `parity`, `final`, `colors`, `polish`, `e2e` and `wave3a` were all contained in `main` and are deleted locally, with their worktrees; three old backup branches remain in the private repository for the owner to delete. The owner's order of work from there: the desktop browser version flawless first, phone and touch after.

## Keeping the docs current

| When | Update |
|---|---|
| At every milestone | Regenerate [STATUS.md](STATUS.md) from the code, the newest agent reports and the newest crawler run, and change its date. |
| At the end of every wave | Add a section to [PROJECT-LOG.md](PROJECT-LOG.md) in the same shape as the others (goal, who, outcome, numbers, problems, commits), fill the matching placeholder, and update its summary table. |
| When something is decided | Append an entry to [DECISIONS.md](DECISIONS.md) with the next free number; when an open question (Q-n) is settled, record the answer there and point to the entry that implements it. |
| When TV behavior is adapted, dropped or fixed | Append a row to the right area in [DEVIATIONS.md](DEVIATIONS.md), with the file and the state. |
| When structure or commands change | Update [ARCHITECTURE.md](ARCHITECTURE.md) (folders, contracts, data flow) and [TOOLING.md](TOOLING.md) (scripts, flags, environment keys), and the root [README.md](../README.md) when the change touches what a user sees or how the app is run. |
| When a production dependency changes | Run `npm run gen:licenses` and update [THIRD-PARTY-NOTICES.md](../THIRD-PARTY-NOTICES.md) by hand from the regenerated list. If a new Apache-2.0 component appears, the list of names in [LICENSE-EXCEPTION.md](../LICENSE-EXCEPTION.md) and in the root README needs the owner's attention. |
| After running the archiver | Re-check numbers taken from the agent logs; counts in these documents are snapshots. |
| Before every public release (the first was on 2026-11-18, the third on 2026-11-24) | A privacy pass over the tree, every file in `docs/` and the specs included: remove credentials, account names, email addresses, real server addresses, machine-specific absolute paths and anything that describes one particular machine, network or server; check that every "in progress" or "planned" statement is still true, and update this page's current-state paragraphs. Then the release is one new commit on the public branch; the private history is never pushed to the public repository ([DECISIONS.md](DECISIONS.md) T-58). |

Each fact lives in one document and the others link to it: decisions in DECISIONS.md, chronology in PROJECT-LOG.md, structure in ARCHITECTURE.md, differences from upstream in DEVIATIONS.md, commands in TOOLING.md, current state in STATUS.md. The root README is the summary for the public and repeats only what a reader needs to decide whether and how to run the app. Builders do not edit these files; they list deviations, fixed bugs, decisions and verification in their reports, and the lead folds those in ([CLAUDE.md](../CLAUDE.md), "Documentation").
